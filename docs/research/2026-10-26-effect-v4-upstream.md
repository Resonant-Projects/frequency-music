# Effect v4 upstream upgrade research

The companion [repo investigation](../effect-v4-upgrade.md) subsequently tested
the Park-scoped override and found identical preset and generated CSS output.

Research only. Repository `AGENTS.md` was read. Public pages were retrieved through Lab Firecrawl; Context7 was resolved to `/effect-ts/effect` and `/websites/effect_website_v4` before querying. Registry metadata and published tarballs provide the release evidence below.

## Findings and recommendation

Effect v4 is stable upstream. Frequency currently has no direct `effect` or `@effect/*` dependency or application import to migrate. Its sole locked Effect installation is `web`'s `@park-ui/panda-preset@0.43.1`, which depends on exactly `effect@3.10.15`. The immediate question is how to update or replace that consumer, rather than how to rewrite Frequency's backend in Effect.

My recommendation is to investigate a maintained preset release or a narrowly owned replacement before considering a transitive override. That is an inference from the current dependency graph, not an Effect recommendation. Adding `effect@4` directly would not satisfy the preset's exact v3 dependency and would normally leave both majors installed.

## Official migration sources and package replacements

The release announcement says to start with [`MIGRATION.md`](https://github.com/Effect-TS/effect/blob/main/MIGRATION.md). Its [generated import/API map](https://github.com/Effect-TS/effect/blob/main/migration/v3-to-v4.md) and focused guides are the primary references. These are moving `main` documents, not a frozen 4.0.6 specification. The retrieved map's comparison head is `399ecbe63f68b8698789190ec3e779315e26e35e`; live main was `20e5ba813ca014bc841672325b5e824b8100d976`. Do not assume every `main` statement shipped in 4.0.6.

Published [`effect@4.0.6` metadata](https://registry.npmjs.org/effect/4.0.6) and its [tarball](https://registry.npmjs.org/effect/-/effect-4.0.6.tgz) were separately inspected. They confirm zero runtime dependencies, ESM exports, the import paths below, `Schema.toStandardSchemaV1`, and native `Arbitrary`. The [`@effect/vitest@4.0.6` tarball](https://registry.npmjs.org/@effect/vitest/-/vitest-4.0.6.tgz) confirms the native property-test options.

| v3 package or import | v4 replacement and qualifications |
| --- | --- |
| `@effect/platform` | Consolidated into `effect`. `@effect/platform/FileSystem` becomes `effect/FileSystem`; `Path` becomes `effect/Path`; `Error` becomes `effect/PlatformError`. |
| Platform HTTP modules | `@effect/platform/HttpClient` becomes `effect/http/HttpClient`; `FetchHttpClient` becomes `effect/http/FetchHttpClient`; `HttpApp` becomes `effect/http/HttpEffect`. Grouped imports use `effect/http`. |
| Platform HTTP API modules | `@effect/platform/HttpApi` becomes `effect/http-api/HttpApi`, and related modules move under `effect/http-api`. |
| Other platform modules | `Command` becomes `effect/process/ChildProcess`; `CommandExecutor` becomes `effect/process/ChildProcessSpawner`; `KeyValueStore` becomes `effect/persistence/KeyValueStore`. Follow each module's map, not a blanket prefix substitution. |
| `@effect/platform-node`, `@effect/platform-bun` | Remain separate, on matching v4 versions. For example `effect@4.0.6` with `@effect/platform-node@4.0.6`. Shared runtime code remains `@effect/platform-node-shared`. |
| `@effect/schema/Schema` | Use `effect/Schema`, or `import { Schema } from "effect"`. This consolidation already happened in v3.10, per the [official weekly release account](https://www.effect.website/blog/this-week-in-effect/38). V4 rewrites Schema APIs further. Lowercase `effect/schema` is a separate grouped module, not the replacement for the core `Schema` import. |
| `@effect/cli` | Consolidated into `effect/cli`. `Args` becomes `Argument`, `Options` becomes `Flag`, and `Command` remains `Command`. This is a redesigned API, not only import changes. |
| `@effect/vitest` | Remains `@effect/vitest`, at the matching v4 version. [`4.0.6` peers](https://registry.npmjs.org/@effect%2fvitest/4.0.6) require `effect:^4.0.6` and `vitest:>=5.0.0 <6.0.0`. Frequency's locked Vitest 5.0.5 fits this range, but its Vite+ integration still needs verification before adding the adapter. |
| `@effect/rpc`, `@effect/cluster`, `@effect/sql`, core `@effect/ai` | Move into `effect/rpc`, `effect/cluster`, `effect/sql`, and `effect/ai`. SQL drivers, AI providers, atom bindings, and OpenTelemetry integration remain separate. |

Official guidance is to update all retained ecosystem packages to matching v4 versions. The [current migration guide](https://github.com/Effect-TS/effect/blob/main/MIGRATION.md#unstable-module-system) says `effect/unstable/http` becomes `effect/http`, and similarly for other groups. The old paths have no compatibility exports. APIs marked `@stability unstable` can break in minor releases; experimental APIs can break in patches. Modules in packages other than `effect` are currently unstable. Stable APIs and APIs without a stability tag follow strict semver. Path consolidation does not itself stabilize an API.

The [installation guide](https://effect.website/docs/v4/getting-started/installation/) requires TypeScript 5.9+, recommends 7, and describes Node 18+, Bun, and Deno support. All four Frequency manifests already declare ESM and TypeScript `^7.0.2`. Concrete adapters can have stricter transitive requirements: `platform-node@4.0.6` depends on `undici:^8.12.2`, whose [published engine](https://registry.npmjs.org/undici/8.12.2) is Node `>=22.19.0`. Check the chosen runtime's complete dependency set.

## API and behavior changes to include in a future migration audit

These are upstream facts, not evidence that Frequency currently uses the APIs. Exact replacements come from the linked focused guides and the generated map. This is a selected audit list, not the complete 1.37 MB rename map.

| Area and source | Exact replacement or changed behavior |
| --- | --- |
| [Services](https://github.com/Effect-TS/effect/blob/main/migration/services.md) | `Context.GenericTag<T>(id)` becomes `Context.Service<T>(id)`. `Context.Tag(id)<Self, Shape>()` and `Effect.Tag` become `Context.Service<Self, Shape>()(id)`. `Effect.Service` becomes `Context.Service` with `{ make }` and explicit `Layer.effect` plus `Layer.provide`. No generated `.Default` or `dependencies` option. Accessors become `yield*` or `.use`/`.useSync`; the guide prefers `yield*`. |
| [Typed recovery](https://github.com/Effect-TS/effect/blob/main/migration/error-handling.md) | `catchAll` becomes `catch`, `catchAllCause` becomes `catchCause`, `catchAllDefect` becomes `catchDefect`. `catchSome` becomes `catchFilter(filter, handler)` using `Filter`, not a callback returning `Option<Effect>`. `catchSomeCause` becomes `catchCauseFilter`; `catchSomeDefect` is removed. |
| Same error guide | Mixed typed failure plus defect skips typed recovery and converts typed errors to defects. Use `catchCause` or `catchDefect` when recovery must include defects. Interruptions beside a typed error do not block typed recovery. Error mappers now map every typed error while retaining defects, interruptions, and reason order. Review retries and finalizer failures, not just compilation. |
| [Cause](https://github.com/Effect-TS/effect/blob/main/migration/cause.md) | Recursive `Empty/Sequential/Parallel` cause nodes become `cause.reasons`, an array of `Fail/Die/Interrupt`. `Cause.sequential` and `parallel` become `combine`, losing the sequence/parallel distinction. `isFailType(cause)` becomes `isFailReason(reason)`. `failureOption` becomes `findErrorOption`; `failureOrCause` becomes `findError`, which returns `Result`. Exception names such as `TimeoutException` become `TimeoutError`. |
| [Forking](https://github.com/Effect-TS/effect/blob/main/migration/forking.md) | `Effect.fork` becomes `forkChild`; `forkDaemon` becomes `forkDetach`. `forkScoped` and `forkIn` remain. Options include `startImmediately` and `uninterruptible`; startup defaults to deferred. Replace removed `forkAll` with individual forks or higher-level concurrency; replace `forkWithErrorHandler` with result observation via `Fiber.join` or `Fiber.await`. |
| [Subtyping](https://github.com/Effect-TS/effect/blob/main/migration/yieldable.md) | `Ref`, `Deferred`, and `Fiber` no longer act as Effects. Use `Ref.get(ref)`, `Deferred.await(deferred)`, and `Fiber.join(fiber)`. `Option` and new `Result` require `Effect.fromOption` and `Effect.fromResult`; neither has `.asEffect()`. `Config` and `Context.Service` remain Effects. |
| [Either map](https://github.com/Effect-TS/effect/blob/main/migration/annotations/effect__Either.yaml) | `Either<A,E>` becomes `Result<A,E>`, `right/left` become `succeed/fail`, `isRight/isLeft` become `isSuccess/isFailure`. Match callbacks become `onSuccess/onFailure`; payload properties `.right/.left` become `.success/.failure`. `Effect.either` becomes `Effect.result`. |
| [Fiber-local state](https://github.com/Effect-TS/effect/blob/main/migration/fiberref.md) | `FiberRef` is removed. Define `Context.Reference<T>(id, { defaultValue })`; read with `yield*`. `Effect.locally(effect, ref, value)` becomes `Effect.provideService(effect, reference, value)`. This is scoped provision, not a mutable `FiberRef.set` substitute. Built-ins move to `References`, for example `References.CurrentLogLevel`. |
| [Runtime](https://github.com/Effect-TS/effect/blob/main/migration/runtime.md) and [scope](https://github.com/Effect-TS/effect/blob/main/migration/scope.md) | `Runtime<R>` is removed. Obtain `Effect.context<R>()` and call `Effect.runForkWith(services)(program)` instead of `Effect.runtime<R>()` plus `Runtime.runFork(runtime)`. `Scope.extend` becomes `Scope.provide`, preserving scope ownership behavior. |
| [Layer memoization](https://github.com/Effect-TS/effect/blob/main/migration/layer-memoization.md) | Nested `Effect.provide` calls reuse layers already built by enclosing provision/runtime. Sibling calls still build separately. `Effect.provide(layer, { local:true })` isolates a subtree; `Layer.fresh` also remains. Official recommendation is still to compose layers and provide once. |
| [Process lifetime](https://github.com/Effect-TS/effect/blob/main/migration/fiber-keep-alive.md) | Core fibers now keep a Node process alive during suspended work. Platform `runMain` remains recommended for signal handling, exit codes, and error reporting. Review worker shutdown behavior if Effect is introduced later. |
| [Equality](https://github.com/Effect-TS/effect/blob/main/migration/equality.md) | `Equal.equals` now compares plain objects, arrays, Maps, Sets, Dates, and regexes structurally by default. `NaN` equals `NaN`. Use `Equal.byReference(obj)` or `byReferenceUnsafe(obj)` when identity semantics are required. `Equal.equivalence` becomes `asEquivalence`. |
| [Schema guide](https://github.com/Effect-TS/effect/blob/main/migration/schema.md) | `decodeUnknown/decode` become `decodeUnknownEffect/decodeEffect`; `encodeUnknown/encode` become `encodeUnknownEffect/encodeEffect`. `decodeUnknownEither/decodeEither` become `decodeUnknownExit/decodeExit`, returning `Exit`, not `Either` or `Result`. `typeSchema/encodedSchema` become `toType/toEncoded`; `annotations` becomes `annotate`; `standardSchemaV1` becomes `toStandardSchemaV1`. |
| Same Schema guide | `Union(A,B)` becomes `Union([A,B])`; `Tuple(A,B)` becomes `Tuple([A,B])`; multi-value `Literal("a","b")` becomes `Literals(["a","b"])`; `Record({key,value})` becomes `Record(key,value)`. Filters become checks such as `String.check(Schema.isMinLength(1))`. `Schema.Date` now expects a Date input; use `Schema.DateFromString` to preserve the old ISO-string decoding contract. `optionalWith` needs option-specific restructuring. |
| Same Schema guide and published Vitest sources | Schema generation now uses `import * as Arbitrary from "effect/Arbitrary"` and `Arbitrary.schema(schema)`. Property-test options `{fastCheck:{numRuns:200}}` become `{arbitrary:{runs:200}}`. Raw fast-check arbitrary inputs are no longer accepted by `@effect/vitest`; use Schema/native Arbitrary inputs or fast-check directly in ordinary Vitest. Seeds, shrinking, and replay tokens do not preserve the old engine's sequences. |
| [CLI map](https://github.com/Effect-TS/effect/blob/main/migration/v3-to-v4.md) | `Command.make` uses one nested config of Argument and Flag values. V3-style `Command.run` accepting argv becomes `Command.runWith`; v4 `run` reads Stdio. `Options.boolean(name)` becomes `Flag.Boolean(name).pipe(Flag.withDefault(false))` to preserve omitted-flag behavior; bare `Flag.Boolean` is required. `Options.all` becomes a config record in `Command.make`. |

## Actual consumers and compatibility objections

Local evidence comes from the four manifests and `bun.lock` files and `web/panda.config.ts`. No `@effect/*` package entries occur in those locks. No direct Effect imports were found in application source. This is a source and lock audit, not an installed-tree or production audit.

1. **Park UI is the concrete blocker.** `web/panda.config.ts` imports `createPreset`, gold, and slate from the preset. The [current registry manifest](https://registry.npmjs.org/@park-ui%2fpanda-preset/0.43.1) pins `effect:3.10.15`; its live `latest` is still 0.43.1, published November 22, 2024. Its [published tarball](https://registry.npmjs.org/@park-ui/panda-preset/-/panda-preset-0.43.1.tgz) uses `Match.value`, `Match.when`, and `Match.orElse` in radius generation. Those names still exist in v4, but this is not proof the complete preset or its ESM and CJS entry points work with v4. An override needs explicit verification of this actual consumer and unchanged generated design tokens. No override experiment was performed.
2. **Standard Schema is an interoperability contract, not a blanket upgrade approval.** [`@standard-schema/spec@1.1.0`](https://registry.npmjs.org/@standard-schema%2fspec/1.1.0) has no Effect dependency. Effect 4.0.6 vendors its type declarations in `src/StandardSchema.ts`. The [official adapter docs](https://effect.website/docs/v4/schema/standard-schema/) describe `Schema.toStandardSchemaV1(schema)` and `~standard.validate`, which can return a synchronous result or a Promise. Sharing this contract does not prove a consumer accepts asynchronous validation, transformations, error paths, JSON Schema conversion, or an Effect schema in place of a Zod-specific interface.
3. **Check every locked Standard Schema consumer.** Root has [`@ai-sdk/provider-utils@5.0.58`](https://registry.npmjs.org/@ai-sdk%2fprovider-utils/5.0.58) and [5.0.62](https://registry.npmjs.org/@ai-sdk%2fprovider-utils/5.0.62), both requiring `^1.1.0`. Agent has [`@langchain/core@1.3.0`](https://registry.npmjs.org/@langchain%2fcore/1.3.0) requiring `^1.1.0`, and [`@langchain/langgraph@1.5.2`](https://registry.npmjs.org/@langchain%2flanggraph/1.5.2) requiring exactly `1.1.0`. [`convex-helpers@0.1.128`](https://registry.npmjs.org/convex-helpers/0.1.128) appears in root, agent, and media with optional peer `^1.0.0`; root's aggregate also locks [0.1.122](https://registry.npmjs.org/convex-helpers/0.1.122) with that optional peer. Root and agent resolve spec 1.1.0. These ranges fit the spec version. They do not establish support for replacing Frequency's existing Zod contracts or SDK integration APIs with Effect Schema.
4. **OpenTelemetry peers are separate from Effect compatibility.** Root and agent lock [`langsmith@0.11.0`](https://registry.npmjs.org/langsmith/0.11.0); agent also locks [0.10.13](https://registry.npmjs.org/langsmith/0.10.13) under langgraph-cli. Both declare optional wildcard peers for API, sdk-trace-base, and exporter-trace-otlp-proto. Root, web, and media lock [`vitest@5.0.5`](https://registry.npmjs.org/vitest/5.0.5), with optional API peer `^1.9.0`. There are no resolved `@opentelemetry/*` package entries in these four locks. A peer declaration alone does not show an installed integration or prove runtime compatibility.
5. **Adding Effect telemetry would introduce its own compatibility work.** [`@effect/opentelemetry@4.0.6`](https://registry.npmjs.org/@effect%2fopentelemetry/4.0.6) requires `effect:^4.0.6`, API `>=1.9.0 <2`, API logs/sdk logs `>=0.203.0 <0.300.0`, resources/metrics/trace SDKs `>=2 <3`, and semantic conventions `>=1.33.0 <2`. Most listed OTel peers are optional; semantic conventions is not marked optional. Verify each actual exporter, resource provider, tracer provider, SDK, and LangSmith integration selected. Some v3 Effect OTLP modules move directly to `effect/observability`, as the import map records, while the OTel SDK integration remains separate. Do not install all OTel peers just because the scope appears in a lockfile.
