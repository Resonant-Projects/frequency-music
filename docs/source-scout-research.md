# Source Scout research discovery and page capture

Source Scout searches against graph gaps, judges candidates, then writes canonical Sources in Convex. The general-web channel is Firecrawl; OpenAlex and Europe PMC add paper-focused discovery without account signup. Results are interleaved under the existing per-query cap so Firecrawl cannot crowd out scholarly records, with DOI/URL dedupe and per-provider audit outcomes. Search hits are candidates, not evidence of a paper's claims. DOI and publication metadata supplied by a search index remain unverified until checked against the publisher or registry. Exa (possibly the requested “Expo”) was evaluated as an optional publication search with a free-credit tier, but not integrated because it needs a separate account/key and these keyless scholarly providers cover the first release; Tavily is a web-search alternative, not an authoritative paper index.

For judged Source candidates, the agent worker may fetch public HTML through Keith's self-hosted Crawl4AI server. The agent-tool `ingestScoutedSource` stores at most 30,000 characters as `rawText` with `metadata.scoutedBy.contentProvider = "crawl4ai"`; the canonical dedupe mutation never overwrites an existing Source, with one exception: a Source the Scout itself created URL-only (still `ingested`, no text) may gain captured text on a later run, recorded as `metadata.scoutedBy.contentProvider` and `capturedByAgentRunId`. Successful content enters `text_ready`, eligible for the existing batch Extraction workflow. Only the source-scout ingest node supplies `rawText` and `contentProvider`. Both are kept out of the LangChain tool schema, and the mutation rejects captured text from any run whose graph is not `source-scout`, so a model cannot assert Crawl4AI provenance. A failed crawl still records the URL-only Source and does not falsely mark it ready. Before crawling, the Scout asks `findExistingSourceUrls` which candidates already own the same canonical URL dedupe key and whether each still awaits capture. Known Sources with text, or from other intake paths, skip page capture because duplicate intake would discard the text. A scout URL-only Source is crawled again, so it recovers after a crawler outage. The Scout emits canonical URLs (DOI lowercased, tracking parameters removed, query sorted), and the preflight also checks the provider's original spelling. When a Source already exists under that spelling, from another intake path, the Scout ingests the original so canonical dedupe matches it. Crawl requests exclude images, and the worker refuses crawl responses larger than 16 MB before parsing. If that preflight fails, the Scout crawls as before and intake still dedupes. Scholarly search keeps a provider's full publication date only; a year-only record carries no `publishedAt`. PDF URLs are not sent to the HTML crawler; PDF/OCR needs a separate intake path. Feed proposals remain disabled until human approval.

## Activation

The agent worker needs `CRAWL4AI_API_TOKEN` in its runtime environment and network access to `https://crawl4ai.rproj.art`. Crawling is disabled by default even with a token: the worker requires `CRAWL4AI_EGRESS_GUARDED=true` after an operator verifies the Crawl4AI deployment enforces private/reserved address blocking at network egress, including DNS resolution, redirects, and cloud metadata targets. The client's initial-host check is not an SSRF boundary. Until that deployment protection exists, leave this flag false and the Scout will ingest URL-only Sources.

Egress verification, 2026-09-29, Crawl4AI 0.9.4 at `crawl4ai.rproj.art`: the 0.9 Docker server validates destinations after DNS resolution and routes Chromium through its pinning egress proxy. `POST /crawl` returned HTTP 400 `URL blocked (SSRF protection)` for `169.254.169.254`, `127.0.0.1`, `[::1]`, `[::ffff:127.0.0.1]`, `0.0.0.0`, decimal and octal loopback forms, `172.16.10.13`, `100.64.0.1`, a Tailscale hostname, and public DNS names that resolve to private addresses (`127.0.0.1.nip.io`, `10-0-0-1.sslip.io`). A public URL that 302-redirects to loopback or the metadata address returned `success: false` with the proxy's `URL blocked` body, which the client discards. A public page crawled normally. That evidence satisfies the gate above for this deployment. Re-verified 2026-09-30 after CT 109 gained a persistent JWT signing key (homelab-infra #585), using the worker's own token: the same private, loopback, metadata, NPM, IPv6 and private-resolving DNS targets returned HTTP 400 `URL blocked`. The public-redirect probes to loopback and the metadata address now report `success: false` at the 302, with Crawl4AI's anti-bot message instead of the proxy's `URL blocked` body; no internal content is returned either way. Re-run the same probes after any Crawl4AI upgrade or configuration change, and keep `CRAWL4AI_ALLOW_INTERNAL_URLS` unset on the server, because that escape hatch disables the protection. The 1Password reference is in `agent/.env.schema` (`Homelab Runtime` vault); the schema documents the contract but the worker does not automatically load Varlock. Supply the token through the worker's existing secret delivery, not source control, a command argument, or a chat message. In production the Kubernetes worker receives a `data` scope client JWT (1Password `Crawl4AI Frequency Worker Token`, never the server's admin token) through its ExternalSecret, with `CRAWL4AI_URL=http://172.16.10.19:11235` and `CRAWL4AI_EGRESS_GUARDED=true` (homelab-infra #586, #589); renewal and revocation are documented in homelab-infra `services/crawl4ai/README.md`. `CRAWL4AI_URL` optionally overrides the default server URL. Firecrawl search uses `FIRECRAWL_API_URL` when set, for example the Lab's self-hosted `http://172.16.10.38:3002`, and sends it no credential. Unset or empty means Firecrawl Cloud, which needs `FIRECRAWL_API_KEY`; that key is sent only to `https://api.firecrawl.dev`. OpenAlex and Europe PMC require no keys; the former has a small anonymous daily search budget, so the Scout caps calls and should be observed for 429s.

Do not run `convex dev`, `run`, `codegen`, or `deploy` just to test this: the repository has one live self-hosted deployment. Unit tests run with recorded/mocked responses. Before activating the worker, verify its secret binding, server reachability from that worker, and deployment preview. After deployment, inspect the agent audit trail and confirm an actual scouted Source has `text_ready`, nonempty `rawText`, and eventually an Extraction with Claims; none of those states follows from a green unit test alone.
