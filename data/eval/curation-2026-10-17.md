## H4 — drop recommended, and a pin is needed either way

H4 (`jh7d82hc6s34cdww0k25sb4gd18aafhv`) has two independent problems.

1. **Claim 4 is wrong, and the reference output repeats it.** H4 states that
   an 8 kHz low-pass removes "more than 80%" of a 44.1 kHz spectrum. Nyquist is
   22.05 kHz, so the figure is ≈63.7%. The error is in an input claim and also
   in the golden `rationaleMd`. The hypothesis dataset scores against that
   reference output, so keeping it rewards the error. That is option (b) on the
   [July sheet](curation-2026-07-18.md#hypotheses--4-candidates-all-provisional-keep).
2. **Its golden content no longer regenerates.** H4 has no `extractionIds`,
   so the materializer takes the newest extraction of its source. A Sonnet 5.5
   re-extraction on 2026-10-13 (`j97endrec2s2xh76xgc92x1t9x8g6qxb`, 2 claims)
   now comes first. The golden row was built from `j97f14ww3grvkgbgx82zppkj5x86hmsg`
   (2026-05-11, 5 claims). A read-only check confirmed its claims, parameters
   and topics equal the golden row's. Re-running the materializer today would
   change H4's `claims`, `compositionParameters` and `topics`. It would also
   change both ratified weekly-brief rows, because each embeds H4.

**Recommendation: (b) drop H4 from `HYPOTHESIS_IDS`.** That leaves 6 rows, over
the floor. Whatever Keith decides, add a pin for H4 to
`j97f14ww3grvkgbgx82zppkj5x86hmsg` in `HYPOTHESIS_EXTRACTION_REPOINTS`. The two
ratified briefs keep embedding H4 even if it leaves the hypothesis dataset, and
the pin keeps both briefs equal to their ratified snapshot. Without the pin, the
drift check reports the briefs (and H4, if kept) as `DRIFT`. The check catches
the drift, but it is avoidable.

## Ratifying (after Keith decides)

Keith's decision is the only human input for this step. The parent task already
authorizes the scoped mechanical work that applies it: the materializer edit,
its read-only production run, and the drift check. This is curation, done
before the sweep. Plan 008's rule that a sweep executor does not edit
`scripts/langsmith/` still holds.

The golden files are generated by
`scripts/langsmith/materialize-curation-2026-07-18.ts`, and a hand edit is
reverted on the next run, so ratification goes through the materializer:

1. Record the decision (accepted ids, the H4 choice) at the top of this sheet.
2. In the materializer, add the accepted ids to `HYPOTHESIS_IDS` with a comment
   naming this sheet, remove H4's id if it is dropped, and add the H4 pin to
   `HYPOTHESIS_EXTRACTION_REPOINTS`.
3. Run the materializer. It reads production through read-only Convex queries
   and rewrites **all three** golden files.
4. Run the drift check in the
   [readiness runbook](../../docs/evidence/eval-baseline-20261017/readiness.md#ratification-and-drift-check).
   It compares every upload key of every regenerated row with the approved
   snapshot: the golden files at `57f7c90` plus the proposed file. It ignores
   the `sources` and `thesis` fields the materializer adds, because the upload
   reads neither. Any changed or unknown row goes back to Keith before upload.
5. Approve the upload by the regenerated files' hashes, not by the hashes of
   this snapshot.
